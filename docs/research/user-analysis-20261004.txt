リポジトリの実験記録と実装を確認したところ、現状は、**「学習・評価・提出準備の土台はできているが、自作モデルの識別性能はまだ弱く、Epoch数を増やす前に切り分けるべき問題がある」**という状態です。
私なら、今の設定をそのまま50 Epochへ延長するのではなく、評価の記録を整える → 事前学習済みモデルで比較する → ラベルと画像の見せ方を改善する → 有望なモデルだけ複数fold・アンサンブルへ進める、という順番にします。
以下では、リポジトリから確認できた結果、コードから分かった問題候補、公開手法から得られる知見、具体的な実験計画を分けて説明します。なお、今回はコードと保存された実験集計を確認したもので、Git管理対象外のMRIキャッシュ・重み・個別予測CSVを取得して再学習・再評価したわけではありません。

競技戦略としては、その0.924の提出を比較基準として保持しながら、自作モデルを改善する進め方が合理的です。

2. コードから分かった、優先して切り分けるべき点
まず、現在のコードには残すべき設計もあります。DICOMの物理座標によるスライス順序の決定、欠損ラベルのmask、goldと重複するgroupの除外、前処理fingerprint、推論時にReportを使わない設計は、改善実験を信頼できるものにする土台です。これらを捨てて、別の大きなNotebookへ全面移行する必要はありません。
そのうえで、私は次の点を優先します。
2.1 最初に試すべきなのは、モデルの大型化より事前学習です
model.pyでは、実際に次の指定になっています。

self.encoder = resnet18(weights=None)
つまり、画像特徴を抽出するResNet18はランダム初期化です。さらにDataset側に画像拡張はなく、同じキャッシュ画像を各Epochで繰り返し見ています。
この条件では、「5 Epochで学べるか」以前に、少数の検査・不完全なラベルから、画像特徴抽出そのものを学び直していることが大きな負担になっています。
最初の比較対象として勧めるのは、ImageNet事前学習済みResNet18＋現在の所見別Attentionです。これなら、現在のキャッシュやモデルの大部分を維持したまま、初期化の寄与を調べられます。Torchvisionには対応する事前学習重みが用意されています。PyTorch Documentation
ただし、現在の入力正規化は[-1, 1]で、Torchvisionの事前学習重みが想定するImageNet正規化とは異なります。重みだけ差し替えて終わりにせず、正規化も明示してください。PyTorch Documentation
要因を切り分けるなら、次の比較がよいです。
比較初期化入力正規化その他AランダムImageNet正規化同じcache・fold・Epoch数・学習率BImageNet事前学習ImageNet正規化Aと同じ
現在のe002は、別に従来条件として残します。こうすると、正規化の変更と事前学習の効果を混同せずに済みます。
なお、configs/baseline.jsonのmodel.backboneを別名にするだけでは、モデルは切り替わりません。現在の実装ではKneeMILがResNet18を直接生成しています。バックボーンを交換する場合は、モデル生成部分と特徴次元を実際に変更する必要があります。
2.2 Batch size 1とBatchNormの組み合わせは、診断する価値があります
現在は、検査単位のbatch sizeが1、勾配蓄積が4です。一方、画像Encoderには、その1検査に含まれる最大24個のwindowがまとめて入ります。
したがって、「BatchNormが1枚だけを見ている」わけではありません。しかし、同じ検査に属する、強く関連した画像だけから、そのforwardの統計量を計算している状態です。
BatchNormは学習時のミニバッチ統計と推論時の移動平均統計を使い分けます。勾配蓄積を4回しても、BatchNormの統計が4検査分まとめて計算されるわけではありません。この違いが学習時と評価時のずれを生む可能性はありますが、現状の悪化原因だと断定はできません。PyTorch Documentation
比較するなら、事前学習モデルを使ったうえで、batch size 1・蓄積4と、batch size 4・蓄積1を比べます。また、事前学習済みBatchNormの統計を固定する実験も候補です。
ここには二つ注意があります。ランダム初期化モデルのBatchNormを無条件に固定することは勧めません。 また、現在は毎Epochでmodel.train()を呼ぶため、統計を固定する実装では、その後もBatchNormだけ評価モードを維持する必要があります。
2.3 学習BCEと検証BCEは、集計方法も違います
これはコード上の、見落としやすい点です。
学習側は、各ミニバッチ内の観測ラベルについて平均BCEを計算し、それを平均しています。現在はbatch size 1なので、概ね「検査ごとの平均損失を平均する」集計です。
一方、検証側は、検証集合全体の観測ラベルの損失を足し、観測セル総数で割っています。つまり「観測セル単位の平均」です。観測ラベル数が検査ごとに異なるため、この二つは一致しません。学習側にはDropoutやBatchNormの動作の違いもあります。
したがって、先ほどの学習曲線の差を、そのまま純粋な過学習量と解釈するのは不適切です。
同じcheckpointをeval()にして、学習側の固定サンプルと検証側を同じ集計方法で評価する処理を追加すると、原因がかなり見えやすくなります。
さらに、batch sizeを変更する実験では、損失の重み付けまで変わらないように注意が必要です。単に1から4へ変えると、BatchNormだけでなく、欠損数の異なる検査の寄与も変わり得ます。
2.4 現在の画像キャッシュは、情報をかなり絞っています
現在の前処理は、最大3系列、各系列8 window、各windowは隣接3スライス、画像サイズ192×192です。各系列全体を1・99パーセンタイルで正規化し、その後、画像全体を正方形へリサイズしています。
ここで気になるのは、次の三点です。
物理的な大きさが統一されていません。
PixelSpacingを使ったmm単位の切り出しがなく、撮像範囲全体を192pxへ縮小しています。検査によって、同じ構造がモデル上で占める大きさが変わります。
スライスの選び方が毎回固定です。
中心位置は系列の先頭から末尾まで8点の等間隔です。最初と最後のwindowでは範囲外インデックスを端へ寄せるため、境界スライスが重複します。コード上、端の2 windowはこの影響を受けます。
同じ撮像面の異なる系列を十分に残していません。
系列選択は、まず異なる撮像面を優先し、最大3系列に制限します。3方向を確保できても、同じ方向の別の撮像条件から得られる情報は削られます。
重要なのは、192pxのキャッシュを後から384pxへ拡大しても、削られた細部は戻らないことです。高解像度化を本格的に評価する段階では、元DICOMから別バージョンのキャッシュを作る必要があります。
2.5 所見別Attentionはすでにあるので、その先を考えるべきです
現在のモデルには、12所見それぞれに異なるwindow Attentionがあります。これはよい点です。「Attentionを追加すれば解決する」という段階ではありません。
ただし、各windowがどの撮像面・撮像条件・スライス位置かを明示する入力はなく、window間の順序を扱うモデルもありません。現在の集約は、windowを入れ替えても結果が変わらない構造です。
改善候補は、撮像面・系列種類・位置を表す特徴を加えること、および系列内の特徴を集約してから検査全体へ集約することです。また、ResNetで空間方向に平均化した後にwindowを集約しているため、局所的な所見が薄まる可能性もあります。
ただし、これらは事前学習と入力画像を整えた後の実験です。今すぐ複雑なTransformerや3Dモデルへ置き換えるより、先に基本条件の改善効果を測る方が、判断しやすいと考えます。

3. ラベルについては、モデル変更と同じくらい重要です
3.1 この競技は「何らかの異常が書いてあれば陽性」ではありません
主催者の説明では、例えばACLやMCLは高グレードの損傷が対象で、低グレードの捻挫や軽い変性は陽性とは限りません。半月板も、内部変性と表面へ達する断裂を区別します。EffusionやBaker’s cystは中等量以上など、所見ごとの基準があり、境界的な画像所見は陰性にする方針が示されています。Kaggle
したがって、ラベル抽出の監査では、単なる肯定・否定だけでなく、重症度、部位、急性か陳旧性か、そして大会の陽性定義を満たすかを確認する必要があります。
これは「現在のラベルが全部間違っている」という意味ではありません。リポジトリにはラベルのstate・値・maskの整合性を検査した記録がありますが、CSVの整合性と、医学的な定義への適合性は別の検査だからです。
3.2 Synovitisは、まず「学習に必要な情報があるか」を疑うべきです
Synovitisはweak検証821検査のうち、観測されているのが101検査だけで、その内訳が陽性100・陰性1です。観測分の陽性率は約99%、欠損率は約87.7%になります。一方、goldでは27／58が陽性です。これらは保存集計から計算できます。
ここで、欠損を全部0へ置き換えるのは勧めません。現在のコードが未観測を損失から除いていること自体は適切です。問題は、「レポートに記載されるケースだけを学習する」ことで、観測される症例が偏っている可能性です。
優先したいのは、明示的な陰性表現を取りこぼしていないか、別言語の表現を拾えているか、Effusionとの混同がないか、そして未言及と明示的陰性を区別できているかの監査です。
なお、weakの陽性率をgoldの陽性率へ機械的に揃えることは解決策ではありません。確認すべきなのは、数値の割合だけでなく、そのラベルが何を意味し、どのような検査で観測されるかです。
3.3 現在のBCEでは、12所見が同じ重みになっていません
検証時の観測セルは合計5,727です。そのうちSynovitisは101セルなので、セル平均BCEにおける比重は約1.76%です。Medial Meniscusは750セルで、約13.10%あります。ところが大会AUCでは、どちらも12分の1の重みです。Kaggle
この違いから、BCEの改善が、12所見平均AUCの改善と一致しない可能性があります。
候補となる損失は、所見ごとに観測ラベル上の平均BCEを計算し、それを平均する形です。
\[ L= \frac{1}{12} \sum_{c=1}^{12} \frac{\sum_i m_{ic}w_{ic}\,\mathrm{BCE}(z_{ic},y_{ic})} {\sum_i m_{ic}w_{ic}} \]
ここで、\(m\)は観測mask、\(w\)はラベルの信頼性に応じた重みです。ただし、これは試すべき候補であって、必ず改善するという意味ではありません。
特に、陰性がほとんどないクラスを強く重み付けしても、陰性を識別する情報は増えません。クラスの重み付けと、ラベルの情報不足は別問題です。実装する場合も、学習集合の統計から重みを決め、少数のラベルが過大な影響を持たないようにする必要があります。
3.4 soft labelは有力候補ですが、「不明＝0.5」ではありません
同じ競技の公開比較実験では、DINOv2を使った3 seedの比較で、soft label側がgold 58検査の評価で全seed上回り、rank平均モデルでは約+0.014の改善が報告されています。ただし、差の95%区間はゼロをまたぎ、明確な優越性までは確認できていません。レポート抽出器の二値ラベルを正解とした別評価では、逆にhard label側が優れていました。Kaggle
これは今回、とても参考になります。weak検証でよいモデルと、公式の画像ラベルへよく適応するモデルは、同じとは限らないからです。
ただし、この公開比較のhard側は未言及も0にしており、欠損をmaskしているあなたの実装とは条件が違います。報告された改善幅をそのまま期待することはできません。
私なら、まず「明示的陽性」「明示的陰性」「大会基準未満」「不確実」「未言及」を保持し、それぞれの扱いを比較します。LLMの回答への自信と、画像上で所見が陽性である確率も同じではありません。適当な中間値を大量に入れるより、根拠となる文と状態を残す方を優先します。

あなたのモデルにも所見別Attentionはあるため、比較すべき差は、画像特徴抽出器、物理スケール、系列の選択、解像度、ラベル、学習方法です。

4.2 同じ競技では、学習を長くするよりスライス選択が効いた例があります
公開されたEfficientNet-B0の比較では、中心付近の隣接スライスと等間隔スライスの比較で、fold 0のAUCに+0.018の差が報告されています。一方、その実験条件では60 Epoch化は約+0.001、EMAは約+0.003、Asymmetric Lossは大幅な悪化でした。Kaggle
この結果を一般則にすることはできません。しかし、今回の優先順位としては、**「学習時間を延ばす前に、何を見せているかを改善する」**方向を支持する材料になります。
また、中心スライスだけを残すことが全所見に最適とは限りません。切り出しや選択を強くしすぎると、周辺にある所見を落とす可能性があるため、全体を残す入力との比較が必要です。
4.3 過去のRSNA優勝解法からは、局所化の考え方が参考になります
2024年のRSNA腰椎MRIコンペの優勝解法は、対象スライス・座標を推定してから、局所を切り出して重症度を判定する段階的な構成でした。分類側ではMILや系列モデルも使っています。Kaggle
今回へそのまま移植できるわけではありませんが、得られる示唆は明確です。全画像を縮小して大きなモデルへ入れるだけでなく、診断に必要な場所を十分な解像度で見せる設計が重要です。
ただし、今すぐ膝の検出器やセグメンテーションまで作る必要はありません。まずmm単位の切り出し、系列の整理、より密なスライス入力を試し、それでも局所所見が弱い場合に空間AttentionやROIモデルへ進むのがよいと思います。

5. 検証方法は、今の良い部分を残しつつ改善したいです
5.1 現在のfoldは再現可能ですが、層化されていません
prepare.pyでは、同一レポートと提供されたgroup情報をまとめ、そのgroupのhashからfoldを決めています。これは再現可能で、groupをまたいだ混入を避ける設計です。一方で、所見の陽性・陰性・欠損率を均等化する分割ではなく、患者単位の独立性も未確認と明記されています。
改善するなら、現在のfoldを消さずに、別バージョンとして、groupを維持した多ラベルの層化分割を作ります。陽性数だけでなく、陰性数と観測数も確認してください。
患者対応情報が利用できる場合は、実際に患者単位の重複を確認します。施設や撮像装置の情報が取れる場合は、それらを分けた検証を補助的に行うと、特定の撮像条件への依存を調べられます。
5.2 gold 58件は、何に使ったかを正確に表現することが大切です
現在のコードは、goldをcheckpoint選択から外しています。これはよい設計です。一方、リポジトリの公開コード監査には、他者の学習Notebookでgold AUCによるcheckpoint選択が行われていたという記録があります。「勾配更新に使っていない」ことと、「モデル選択からも独立している」ことは別です。
さらに、今後goldの成績を見ながらラベルやモデルを何度も変更すれば、コード上で選択に使っていなくても、人間の判断を通して開発に利用したことになります。
ここで必要なのは、goldを一切見ないという極端な方針ではありません。開発用として使ったなら、そのように記録し、「独立した最終評価」と呼ばないことです。レポートを人手で監査した評価集合も、画像を専門家が判定したgoldの代わりにはならない点を区別してください。
5.3 公開モデルを、自分のランダム分割でOOF評価してはいけません
公開モデルがweak全体で学習されている場合、その後あなたが作った検証foldも、公開モデルにとっては学習済みデータになり得ます。公開モデルと自作モデルを同じ821件で比較できても、両者が同じ独立性を持つとは限りません。
同じ問題は、公開モデルを教師にした蒸留にもあります。教師が検証データを見ている場合、その予測を使った評価には注意が必要です。
したがって、公開モデルは提出用の比較基準、自作モデルは自分で管理した分割上の比較、という二つをまず分けます。独立したOOFが作れるモデル同士はそこで比較し、公開重みを含む比較は、その制約を記録して扱うのが現実的です。

最初の実験に追加したい記録
最初にruntime.pyへ追加したいのは、各Epochのweak予測CSVと所見別AUCです。現在は最良BCE時の予測だけが残るため、BCEが悪化したEpochで順位付けが改善していたかを後から調べられません。
あわせて、所見別の予測平均・標準偏差、陽性／陰性ごとの予測分布、観測数を保存します。これにより、「ほぼ定数を出している」「順位はよいが確率がずれている」「特定クラスだけ壊れている」を区別できます。
少数の検査だけを使い、画像拡張なしで十分に学習させる動作確認も有用です。それすら学習できない場合は、モデル容量より先に、UIDから系列・キャッシュ・ラベル・予測までの対応を再点検します。
新キャッシュの初期案
新キャッシュは、まず現在の3系列を保ち、mm単位の切り出しと288pxまたは336px程度の解像度を評価するところから始めるのがよいと思います。その後に系列数やスライス数を変えます。最初から全部を変えると、何が効いたか分からなくなります。
保存する情報には、画像だけでなく、系列種類、撮像面、スライス位置、pixel spacing、採用・除外理由も含めたいです。左右や向きの処理、拡張時の幾何変換は、複数スライス間の対応を保つようにします。
また、切り出しが成功した割合、関節が切れていないか、周辺の所見が落ちていないかを目視確認します。リポジトリには全件キャッシュの読み取り成功記録がありますが、これは全画像の内容品質を確認したこととは別です。
計算資源の使い方
現在の実験記録では、5 Epochの学習関数全体が約18分でした。ただし、これは現在の192px・24 windowの構成での実測であり、高解像度化後にも同じ時間で済むわけではありません。
今は、全候補を最初から5-foldで回すより、固定foldで比較し、有望なものだけ別foldとseedで確認する方を勧めます。batch sizeやDataLoaderの並列数も、実MRIでのVRAM・読み込み時間・GPU待ち時間を測って決めます。より高価なGPUを追加する判断は、その後でよいと思います。

7. メダルを狙う戦略として、何を優先するか
公開モデルの基準を保持し、自作モデルには「追加する理由」を求めます
現状の自作モデルを、Public 0.924のモデルへ単純に50対50で混ぜる根拠はありません。単体性能が弱いモデルでも補完的に働く場合はありますが、それは確認して初めて言えることです。
自作モデルが改善してきた段階で、異なるバックボーン、異なるラベル、異なる画像入力が、既存モデルとは違う誤り方をしているかを調べます。そのうえで、少数の固定した重みで確率平均とrank平均を比較します。58検査だけで12所見それぞれの重みを細かく最適化することは、私は避けます。
また、単体モデルに対して、順位を変えない確率補正をしてもAUCは改善しません。確率補正がアンサンブルへ影響することはありますが、現在の優先課題は、出力の見栄えよりも正しい順位付けを学習することです。AUCのこの性質は、公開ベースライン作者の解説でも整理されています。Pilkwang’s Bagel&Coffee
ラベルの利用条件は、精度改善と並行して解決してください
現在のweakラベルはCC BY-NC 4.0で、リポジトリでは非商用ローカル研究として採用し、競技提出への利用可否を未確認としています。今回も、このラベルについて提出利用の可否を確定できませんでした。
CC BY-NCには非商用の制約がありますが、そこから「賞金コンペだから必ず禁止」「学習用だから必ず許可」のどちらも、この場では断定しません。作者の許諾と大会側の条件を確認する必要があります。主催者も、外部データが大会ルール上利用可能かという問題と、データ提供者側の利用規約を満たすかという問題を分けて説明しています。Creative Commons
解決を待つ間も、許容されている範囲の研究実験やコード改善は進められます。別ラベルへ切り替える場合は、ライセンスだけでなく、生成方法とgold利用歴も記録してください。
締め切りに向けては、最後までモデルを変更し続けない方がよいです
公式掲載の期限を日本時間へ直すと、参加・チーム統合は2026年10月16日08:59、最終提出は10月23日08:59です。Publicはテストの約30%、最終順位は残り約70%に基づくため、Publicの小さな改善だけへ過度に合わせるのは避けたいところです。Kaggle
進め方の目安としては、最初に評価と事前学習、次にラベルとキャッシュ、その後に有望なモデルの再確認、最後は提出版の固定と実行確認へ移ります。最終期限は日本時間の朝なので、前夜までモデル改造を続ける計画にはしない方が安全です。

最終的な判断
今のリポジトリには、実験を比較可能にする土台があることが大きな強みです。一方で、現在の結果からは、ランダム初期化ResNet18を長く回すだけで強い競技モデルへ近づく、と考える根拠はありません。
私が最も優先するのは、次の三つです。

1. 各EpochのAUC・予測分布・同じ集計方法の損失を記録し、何が起きているか見えるようにする。.
2. 既存キャッシュのまま事前学習済みResNet18を比較し、画像から学習できる基本条件を確立する。.
3. Synovitisなどのラベルの情報不足と、192px・3系列・固定スライス選択による情報削減を改善する。.
その後に、DINOv2などの別モデル、局所的な画像の集約、複数fold、アンサンブルへ進めます。
次の一手としては、「Epochを増やす」ではなく、「評価ログを追加した事前学習ResNet18の対照実験」が最も勧めやすいです。 その結果を見れば、主な制約が初期化・学習動作にあるのか、それともラベルと画像キャッシュにあるのかを、今よりずっと明確に判断できます。
